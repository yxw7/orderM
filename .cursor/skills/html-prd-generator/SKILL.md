## 2. HTML页面输出
### 2.1 数据存储方案
禁止直接在script拼接JSON，统一使用 `<template>` 存储页面独立需求数据，放置于页面 `</body>` 标签前：
```html
<template id="prd-data-{{pageId}}">
{
  "title": "页面业务名称",
  "items": [
    {"id": "5.2.5.1", "htmlContent": "<p>预编译纯HTML富文本内容</p>"}
  ]
}
</template>
<script>
(function() {
  // 全局累加存储，多页面互不覆盖
  window.PRD_DATA_MAP = window.PRD_DATA_MAP || {};
  const pageId = '{{pageId}}';
  const template = document.getElementById(`prd-data-${pageId}`);
  if(template) {
    try {
      window.PRD_DATA_MAP[pageId] = JSON.parse(template.textContent);
    } catch(err) {
      console.error(`页面${pageId}PRD数据解析失败`, err);
    }
  }
})();
</script>
```
- `htmlContent` 要求：提前将Markdown预编译为原生HTML标签，内置内联样式；前端JS直接赋值 `innerHTML`，**前端禁止二次解析Markdown**；
- template原生文本自动转义引号、换行、特殊符号，无需人工额外转义，规避JSON语法报错；
- 特殊字符强制转义：`</script>` 转为 `\u003c/script>`，防止模板提前闭合。

### 2.2 全局固定UI组件
所有HTML页面自动嵌入两套固定组件，仅内部业务内容可自定义：
1. 「PRD说明」悬浮按钮
    ```css
    position: fixed; top: 20px; right: 20px; z-index: 9999;
    ```
2. 右侧抽屉面板
    - 遮罩：全屏半透明黑色遮罩
    - 抽屉容器：固定宽度600px、白色背景、右侧滑入动画、内部纵向滚动条
    - 操作控件：抽屉右上角关闭X按钮；点击遮罩/X均可关闭面板
3. 关闭逻辑强制约束：
    每次关闭抽屉时，销毁遮罩&抽屉DOM、清空容器innerHTML、解绑全部事件监听，避免多次打开造成事件内存堆积。

### 2.3 抽屉面板内容排版规范
- **【顶部标题栏】**：需求编号 + “模块名称（需求描述）”。下方有一条浅灰色细分割线。需求编号同prd.md 中的 `[章节编号]` 一致。如果内容超过一屏，在顶部标题栏下方自动生成子功能的锚点文字链。
- **【Markdown 深度渲染】**：
  - 段落与间距：行高 1.6，段落间距 12px，确保长文本不拥挤。
  - 重点突出：使用 `**粗体**` 强调核心逻辑，`*斜体*` 用于辅助说明，`` `代码` `` 表示字段名、参数名。若原文档中有高亮背景，可用 `<mark>` 标签模拟。
  - 层级展示：严格保留多级无序列表 (-) 或有序列表 (1.) 的缩进层级。
  - 引用说明：PRD文档中的引用块 (`> blockquote`) 须在面板内以浅灰色左边框形式展示。
- **【核心板块】**：采用“小标题：内容”排版，涵盖：显示样式、交互与排序、业务定义、备注等。
- **【视觉增强】**：涉及状态色（如：绿色、红色）时，在文字前加上对应的彩色圆点图标。状态圆点必须使用内联样式实现，例如 `<span style="display:inline-block;width:8px;height:8px;border-radius:50%;background:#52c41a;margin-right:6px;"></span>`，确保纯HTML环境下也能正常显示。

### 2.4 业务文案书写规范

**字段命名**

- 统一格式：**中文业务名（英文字段名）**，例如：实际关联书目记录号（actualBibRecordNos）、发订时间（issueTime）。
- 表格「字段」列、业务规则中的数据项均按此格式书写；不得仅写英文字段名或仅写中文名（界面纯展示列可只写中文列名）。

**业务规则描述**

- 用「若…则…」「优先…否则…」「当…时…」等自然语言描述业务逻辑。
- **禁止**在 PRD 正文中直接写代码函数名、模块文件名、内部变量名、mock 数据集名称（如 `sortOrderLinesByIssueTimeDesc`、`bibRelatedOrderLines`）。
- 技术实现细节（组件名、路由、缓存 key）仅可写在「实现文件」「路由」等实现触点章节，不写进业务规则与抽屉说明正文。
- 用户可见提示文案可原文引用（如「请先选中书目」）。

**示例**

| 不推荐 | 推荐 |
|--------|------|
| 按 bibRecordNo 过滤 bibRelatedOrderLines | 若用户选中书目，则仅展示书目记录号（bibRecordNo）与当前书目一致的订单行 |
| 调用 sortOrderLinesByIssueTimeDesc | 若无发订时间（issueTime），则排在最上方；否则按发订时间倒序；若发订时间相同，则按订单行号（orderLineNo）升序 |
| discount 字段默认带出 | 若用户选择供应商，则折扣（discount）默认取该供应商在主数据中配置的默认值 |

# Workflow A: 初始化PRD (Initialization)
触发场景：用户提供html和页面实现内容，要求开始生成需求说明。

## 触发条件
全新页面HTML代码、无历史prd.md，从零生成全套需求文档+页面抽屉组件
## 数据源优先级
HTML页面内UI、交互、字段校验、弹窗逻辑为**第一事实源**；若与用户文字需求冲突，以HTML为准，变更摘要增加冲突警告。

### Step1 解析PRD模板骨架
读取模板文件生成完整章节编号树；无模板启用内置通用PRD结构并提示。所有需求点必须归类至对应章节，不允许游离无归属章节。

### Step2 模块化需求聚合拆分
1. 整合逻辑：在生成前，必须先对html页面的需求点进行逻辑分组，将属于同一功能区域的需求整合至一个需求编号。
 - 聚合判定标准：**是否共享同一个 UI 容器且操作入口相邻**（如同一表格的操作列、同一筛选栏、同一标签页容器）。
 - 反例（不应聚合）：两个需求属于完全不同的业务实体（例如“用户头像上传”与“密码修改”），即便在同一卡片内也应分开标注。
2.零丢失提取：整合后的需求说明必须包含该模块下所有原始描述、业务逻辑、前置条件及异常流程，严禁概括或删减细节。

### Step3 并行内容渲染
对于聚合后的每个需求模块（即一个功能点），在推理上下文中**维护一份统一的内容模型**（包含：功能描述、交互逻辑、字段规则、异常处理等），然后同时生成两套格式：
- MD 片段：符合 Markdown 规范的纯文本，用于写入 `prd.md`。需包含标题层级、`**粗体**`、`- 无序列表`、`1. 有序列表`、`| 表格 |` 以及 `> 引用块`。
- HTML 片段：将上述 Markdown 所表达的富文本内容，直接写成**带内联样式的 HTML 标签字符串**（如 `<p><strong>...</strong></p>`、`<ul><li>...</li></ul>`、`<span style="color:red;">...</span>`），用于前端抽屉直接 `innerHTML` 渲染。
**重要**：两段内容必须**逻辑一致**，但格式各自独立。

### Step4 文档写入与数据挂载
- 将所有 **MD 片段** 按章节树拼接，生成完整的 Markdown 文档，写入 `docs/prd.md`。
- 将所有 **HTML 片段** 按页面分组，构造为 JSON 数组（数组元素包含 `id`（章节编号）和 `htmlContent`（编译好的 HTML 字符串）），填入 `<template id="prd-data-{{pageId}}">` 中，写入对应的 `index.html` 文件。


# Workflow B: PRD内容更新 (Incremental Update)
## 触发条件
已有prd.md与HTML文件，用户提供修改后的页面/需求，做增量迭代更新。
## 数据源优先级
HTML页面逻辑优先级高于现有prd.md，冲突直接覆盖原有PRD内容并标注警告。

### Step1 基准数据读取
先读取现有 `docs/prd.md`、HTML内template存储的历史PRD数据，作为新旧对比基准。

### Step2 差异识别
自动对比新旧页面/需求，区分三类变更：新增功能、修改原有功能、废弃旧功能。

### Step3 样式锁定边界：
   - **不可变（样式锁）**：抽屉容器的宽度（600px）、背景色（#fff）、z-index层级、遮罩透明度、按钮固定位置、滑入动画时长。
   - **可变（业务逻辑）**：`htmlContent` 内部的所有内联样式（如状态颜色、文字粗细、圆点颜色等）属于业务表达，允许随需求变更而调整。

### Step4 精准内容替换：
1.根据变更点，更新对应需求模块的**内容模型**。
2.然后重新生成该模块的 **MD 片段** 和 **HTML 片段**：仅针对受影响的需求编号，更新 `prd.md` 中对应章节的内容，并同步更新面板内的 `htmlContent`。
   - **删除项**：将该功能点标记为 `【已废弃】`（如 `【5.2.5.1 XXX（已废弃）】`）。**保留其原有编号和描述内容**。**禁止重用已废弃的编号**。废弃项在面板内须以 **`<details>` 折叠标签** 呈现，默认折叠，保持面板清爽。
   - **新增项**：按既定样式规范生成新编号，在所属章节下取同层级章节当前最大子编号 +1（例如所属章节为 3.2，已有 3.2.1、3.2.2，则新增 3.2.3；若尚无子编号，则从 3.2.1 开始）。确保编号逻辑连续。严禁修改或删除模板中已有的非空章节标题，若某章节内容为空，应保留标题并标注“无”。
   - **修改项**：直接替换该编号下的内容，编号保持不变。
   - **空章节处理**：模板自带的空章节仅保留标题，内容标注「无」，禁止删除章节标题。
	 
### Step5 同步写入
仅更新变更对应的PRD章节与template内对应htmlContent，未改动内容保留不变；嵌入完整抽屉交互组件，输出变更摘要。

# 强制执行自检清单
1. 工作流匹配校验：确认执行的是初始化/增量更新，逻辑无混淆；
2. 需求聚合校验：无错误合并、无错误拆分功能模块；
3. 内容一致性校验：prd.md章节与抽屉htmlContent编号、业务描述100%匹配，无信息遗漏；
4. 抽屉样式校验：内联标签、层级列表、状态圆点、引用块渲染规范；
5. 增量更新专属校验：抽屉容器锁死参数未被修改；
6. 冲突仲裁校验：HTML与PRD冲突时是否输出冲突警告；
7. 特殊字符转义校验：htmlContent中 `</script>` 已转义，template无闭合报错；
8. 文件落盘校验：prd.md、HTML均已完成写入更新；
9. 页面交互校验：右上角PRD按钮正常显示；抽屉开闭、遮罩关闭、事件销毁逻辑正常；重复开闭无内存事件堆积；
10. 跨页面隔离校验：使用 `window.PRD_DATA_MAP` 对象累加存储，页面通过 `data-page-id` 独立读取数据，不存在数据覆盖。
