## 1. 背景与问题

导入任务在 **异步匹配完成** 时，会为每条发货行绑定若干 **馆址订单行**，并基于当时的 **待收套数** 做馆址拆分与默认处置分配。匹配结果以 **任务快照** 形式保存在 `childrenDraft` 中。

订单行是 **全局共享资源**：在任务处于「匹配中 / 待核对 / 核对中」期间，其他用户可能通过逐条收货、其他验收单、其他导入任务等途径 **先一步收走** 部分或全部待收套数。

若仍按匹配快照提交，会导致：

- 对已无待收的订单行写入收货/换货/退货；
- 处置合计超过实时待收；
- 业务数据不一致。

本设计在 **提交瞬间** 对实时订单行做强校验，冲突则 **整批阻断**，由用户调整后再提交。

---

## 2. 目标

- 提交前 **不锁定** 订单行（他人可正常收货）。
- **仅在点击「提交」时** 拉取实时订单行并校验。
- 勾选批次内 **任一冲突 → 整批不提交**（原子提交）。
- 返回可操作的冲突明细，引导用户改套数 / 删子行 / 换行 / 删发货行。
- **不重算** 发货主行匹配状态（success / partial / fail / over 保持不变）。

## 3. 非目标

- 匹配完成时软锁定或预留待收（方案 C）。
- 核对期间定时刷新待收并自动改数（方案 B / D）。
- 提交部分成功（方案 ②）。
- 独立的「检查待收」预检按钮（方案 ③，后续可加）。

---

## 4. 方案选型

| 方案 | 说明 | 结论 |
|------|------|------|
| **① 提交原子校验** | 提交时查实时待收；有冲突则整批失败 | **采用** |
| ② 提交部分成功 | 仅成功行写入 | 不采用 |
| ③ 提交前预检按钮 | 额外主动校验入口 | 不采用（后续可选） |
| 匹配时软锁定 | 占用待收到任务结束 | 不采用 |

## 5. 冲突检测规则

### 5.1 检测时机

**唯一强校验点**：用户点击「提交」，服务端处理 `POST /delivery-import/tasks/{id}/submit` 时。

不在以下环节做实时占用校验：

- 异步匹配引擎写快照；
- 草稿自动保存（400ms 防抖）；
- 添加 / 删除订单行（仍用匹配时或选行时的快照待收做 **表单校验**，见 §7）。

### 5.2 实时数据范围

对每条待校验子行，按 **原 spec §5.1** 相同上下文查询 **当前** 订单行：

- 订户、资源类型、语种、采选方式、供应商；
- 以 `orderLineNo`（订单行号）精确匹配。

查询结果记为 **实时行** `liveLine`。

### 5.3 冲突类型

对每条 **待提交发货主行** 的每个 **child**（馆址订单行）：

| 类型 | 代码 | 条件 | 用户可见说明 |
|------|------|------|--------------|
| 订单行不存在 | `not_found` | 实时库无此 `orderLineNo` | 订单行不存在或已不可收 |
| 不可收 | `not_receivable` | 实时行状态 ∉ {已发订, 处理中} | 订单行状态已变更，不可收货 |
| 无待收 | `no_pending` | 实时 `待收套数 ≤ 0` | 已被他人收完 |
| 待收不足 | `pending_insufficient` | `收货+换货+退货 > 实时待收` | 待收不足（展示快照待收、实时待收、本次处置） |

其中「本次处置」= 子行 `receive + exchange + ret`（与 §9.4 一致）。

### 5.4 原子提交

一次提交请求中，用户勾选的所有发货主行（当前 Tab、未提交、`submitStatus=pending`）：

1. 先执行既有 **快照校验**（`validatePreviewStep`：原因必填、处置 ≤ 快照待收等）；
2. 再执行 **实时冲突校验**（本节）；
3. **任一步失败 → 整批不写入**，所有勾选行保持 `submitStatus=pending`；
4. 全部通过 → 批量写入收货/换货/退货，勾选行置 `submitted`。

## 6. 提交失败交互

### 6.1 错误响应结构（API / 原型）

```json
{
  "ok": false,
  "errors": ["人类可读汇总…"],
  "conflicts": [
    {
      "shipmentLineId": "…",
      "shipmentRowNo": 3,
      "orderLineNo": "st00120250921005-3",
      "location": "华威桥",
      "type": "pending_insufficient",
      "snapshotPending": 2,
      "livePending": 1,
      "disposalTotal": 2
    }
  ]
}
```

### 6.2 前端展示

- 弹窗展示冲突列表（发货行序号、订单行号、馆址、原因）。
- **可选（推荐）**：冲突子行在下区订单行列表 **标红**；直至用户修改或删除后清除标记。
- **不自动** 调低套数或删除子行；由用户确认后再次提交。

### 6.3 用户恢复手段

| 操作 | 说明 |
|------|------|
| 调低处置套数 | 使合计 ≤ 实时待收（用户需自行判断，提交时再次校验） |
| 删除订单行 | 去掉不可用子行 |
| 添加订单行 | 换其他馆址行；追加后仍按 §6.1 分配 |
| 删除发货主行 | 整行不再提交 |

主行 **匹配状态不重算**（沿用现有规则）。

## 7. 与快照校验的关系

| 校验层 | 时机 | 数据源 | 失败后果 |
|--------|------|--------|----------|
| 快照表单校验 | 提交前（客户端 + 服务端） | 任务 `childrenDraft` 内 `pending` | 阻断提交 |
| **实时冲突校验** | 提交时（服务端） | 订单行 **当前** 待收与状态 | 阻断提交 |

说明：

- 核对期间 UI 仍展示 **匹配快照** 中的待收（下区列表 **不展示** 待收列，见 preview spec）；实时待收仅在 **提交失败** 时通过冲突明细告知。
- 快照校验通过但实时校验失败时，以 **实时校验** 为准。

## 8. 数据与实现要点

### 8.1 服务端

- `submitTaskTab` / `POST .../submit` 增加 `validateLiveOrderLines(task, linesToSubmit)`。
- 实时查询复用订单行服务（同 §5.1 过滤条件），**禁止** 仅读任务内 `orderLineData` 快照作为提交依据。
- 事务：校验与写入在同一事务；失败则零写入。

### 8.2 原型（mock）

- `getMatchableOrderLines(ctx)` 模拟实时池；可增加测试开关模拟「提交时待收已减少」。
- 文件名含 **「提交冲突」** 时，模拟 `pending_insufficient` 冲突（与「提交失败」演示并列）。

### 8.3 并发边界

- 两用户 **同时提交同一订单行**：数据库层应以订单行乐观锁/行级锁保证 **仅一方成功**；后提交方收到 `pending_insufficient` 或 `no_pending`。
- 本设计 **不要求** 匹配时占库。

---

## 9. 测试要点

1. 匹配完成后、提交前，他人收走部分待收 → 提交阻断，整批未置「已提交」。
2. 冲突明细含快照待收、实时待收、处置合计。
3. 同一批次多条发货行，仅一条冲突 → **整批** 不提交。
4. 用户调低套数至 ≤ 实时待收后，再次提交成功。
5. 用户删除冲突子行后，再次提交成功。
6. 主行匹配状态在冲突前后 **不变**。
7. 实时行 `not_found` / 状态不可收 / 待收为 0 三类提示文案正确。
8. 并发双提交：仅一方成功（集成/后端测试）。

## 10. 决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 占用策略 | **不锁定**，提交时校验 | 不阻塞他人正常收货 |
| 检测时机 | **仅提交** | 用户选 A |
| 批次策略 | **原子提交** | 用户选 ①；与勾选批量一致 |
| 失败处理 | 提示 + 用户手动改 | 不自动降级套数 |
| 匹配状态 | 冲突时不重算 | 沿用现有 spec |
