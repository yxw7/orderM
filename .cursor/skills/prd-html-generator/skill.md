#输出格式
具体要求如下：
1. **PRD 文件（prd.md）**：必须包含一级标题 `# 订单管理系统PRD`，每个页面使用二级标题 `## 页面名称`，该页面下的每个需求点使用三级标题 `### 需求 [序号]. [模块名]`（序号在该页面内从 1 开始自增）。 若存在同名页面（如“详情页”），建议在 prd.md 的二级标题 ## 后加上文件名后缀，如 ## 订单列表页 (order-list.html)
   *注意：prd.md 中的 `[序号]` 与 HTML抽屉面板中显示的 `[序号]`（两位数，如01）一一对应。*
2. **数据挂载**：必须在HTML文件底部生成 `<script>` 代码块，定义 `window.PRD_DATA = { "page-id": { title: "页面名", items: [ { id: "01", htmlContent: "..." } ] } }`。
   - **重要**：`htmlContent` 的值必须是 **已编译好的纯 HTML 字符串**（即 AI 已将 Markdown 语法转换为 `<p>`、`<ul>`、`<span style="...">` 等标签），客户端 JavaScript 直接将该字符串赋值给抽屉容器的 `innerHTML`，禁止在前端二次解析 Markdown。
   - **触发器位置**：必须在每个页面（`html/pages`下的目标HTML文件）的**右上角**生成“PRD说明”文字链接/按钮。建议使用 `position: fixed; top: 20px; right: 20px; z-index: 9999;` 样式确保其始终悬浮于页面右上角，便于研发随时点击。
   - 点击“PRD说明”时，从该对象中取当前页面的数据渲染右侧抽屉面板。面板右上角显示X关闭按钮或者点击遮罩关闭。
3. **变更摘要**：在聊天界面仅输出简要的变更摘要，格式如下：
✅ 已更新文件：
- index.html（新增/覆盖）
- prd.md（已注入需求编号）


# Task
深度解析前端页面逻辑或者用户提供的需求说明内容，将所有需求点整合后挂载到前端页面。根据用户的明确指令，选择并执行以下两个工作流之一。核心指标：研发人员通过点击PRD说明获取的信息必须足够详实，足以完全替代阅读原始 PRD 文档。

# Task Decision (任务判定)
在执行任何操作前，你必须首先判定用户的意图。
- 如果指令不明确：严禁擅自执行。你必须主动向用户提问：“请问您是需要执行【Workflow A:初始化PRD】（针对新页面/新文档），还是执行【Workflow B: PRD内容更新】（针对已有需求说明内容的增量修改）？”
- 如果指令明确：请严格按照下方对应的工作流执行。



# Workflow A: 初始化PRD (Initialization)
触发场景：用户提供html 和页面实现内容，要求开始生成需求说明。

**数据源优先级（重要）**：
- 以 `html/pages` 目录下目标 HTML 文件中呈现的 **UI 元素、交互逻辑、字段校验** 为 **第一事实源**。
- `docs/订单管理系统需求规格说明.docx` 仅当用户提出参考该文档某个章节内容时才需要去读取其内容。若其内容与 HTML 实际实现逻辑冲突，请询问用户以哪个逻辑为准；若用户未提供该 DOCX 文件，则直接忽略该路径，完全基于 HTML 逆向推导需求。

## 1. 模块化需求聚合 (Modular Aggregation)
- **整合逻辑**：在生成前，必须先对html页面的需求点进行逻辑分组，将属于同一功能区域的需求整合至一个需求编号。
- 聚合判定标准：**是否共享同一个 UI 容器且操作入口相邻**（如同一表格的操作列、同一筛选栏、同一标签页容器）。
- 反例（不应聚合）：两个需求属于完全不同的业务实体（例如“用户头像上传”与“密码修改”），即便在同一卡片内也应分开标注。
- **零丢失提取**：整合后的需求说明必须包含该模块下所有原始描述、业务逻辑、前置条件及异常流程，严禁概括或删减细节。

## 2. 交互面板：全量信息架构 (Comprehensive Tooltip)
为了提升研发人员的阅读体验，需求说明面板内容必须遵循以下排版规范：
- **【顶部标题栏】**：需求编号 + “模块名称（需求描述）”。下方有一条浅灰色细分割线。相同页面的需求编号按照[01]、[02]依次编号。
- **【Markdown 深度渲染】**：
- 段落与间距：行高 1.6，段落间距 12px，确保长文本不拥挤。
- 重点突出：使用 `**粗体**` 强调核心逻辑，`*斜体*` 用于辅助说明，`` `代码` `` 表示字段名、参数名。若原文档中有高亮背景，可用 `<mark>` 标签模拟。
- 层级展示：严格保留多级无序列表 (-) 或有序列表 (1.) 的缩进层级。
- 引用说明：PRD文档中的引用块 (`> blockquote`) 须在面板内以浅灰色左边框形式展示。
- **【核心板块】**：采用“小标题：内容”排版，涵盖：显示样式、交互与排序、业务定义、备注等。
- **【视觉增强】**：涉及状态色（如：绿色、红色）时，在文字前加上对应的彩色圆点图标。状态圆点必须使用内联样式实现，例如 `<span style="display:inline-block;width:8px;height:8px;border-radius:50%;background:#52c41a;margin-right:6px;"></span>`，确保纯HTML环境下也能正常显示。


# Workflow B: PRD内容更新 (Incremental Update)
触发场景：用户提供调整后的html或页面实现内容，要求更新现有需求说明。在执行增量更新前，先读取当前html 文件，解析其中已存在的需求说明内容，作为对比基准。

**数据源优先级（重要）**：
- 以 `html/pages` 目录下目标 HTML 文件中呈现的 **UI 元素、交互逻辑、字段校验** 为 **第一事实源**。
- `docs/订单管理系统需求规格说明.docx` 仅当用户提出参考该文档某个章节内容时才需要去读取其内容。若其内容与 HTML 实际实现逻辑冲突，请询问用户以哪个逻辑为准；若用户未提供该 DOCX 文件，则直接忽略该路径，完全基于 HTML 逆向推导需求。

1. **差异识别**：对比现有内容与调整后html页面实现，识别需求的“新增、修改、删除”变化。
2. **样式锁定 (Style Lock)**：严禁修改任何视觉样式参数。保持颜色、尺寸、面板背景等完全不变。
3. **精准内容替换**：仅针对受影响的需求编号，更新其面板内的 Markdown 文本。
   - **删除项**：将该功能点标记为 `【已废弃】`，**保留其原有编号和描述内容**，并从活跃列表中移除，统一移动到该页面章节的 **最末尾「附录：已废弃需求」** 子章节下。**禁止重用已废弃的编号**。
   - **新增项**：按既定样式规范生成新编号，编号取当前页面下**最大编号 +1**，确保编号逻辑连续。
   - **修改项**：仅替换面板内容，编号保持不变。
4. **重新生成反向文档**：将更新后的需求说明写回 `prd.md`。**必须包含所有历史编号**（含已废弃项，放于附录），确保编号永久可追溯。

# Execution & Self-Correction (强制自检)
任务完成后，必须自检并修正以下项目：

- **指令对齐**：我执行的是【初始化】还是【更新】？
- **聚合自检**：是否有不应聚合却聚合的情况？
- **完整性自检**：面板信息是否详实到可以完全替代 PRD 文档？是否有需求缺失？
- **样式自检**：层级是否正确？面板是否完美保留了PRD文档的 Markdown 层级与重点？
- **样式锁自检（仅更新时）**：无论内容如何变化，视觉参数（颜色、尺寸、偏移量）是否保持了 100% 的一致性？
- **反向写入自检**：需求说明是否已正确写回 `prd.md` 并保存？ 
- **交互与可访问性自检**：点击“PRD说明”按钮是否正确打开并加载对应页面的需求说明面板？是否能通过 右上角X 按钮关闭（或者点击遮罩关闭）？
- **性能与内存自检**：面板的创建/销毁是否避免内存泄漏？
